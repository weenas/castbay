# 电脑接收端（Windows / Linux）技术评估

状态：评估，未开工。回答三件事：做得出来吗、要多少工作、值不值得（见最后的建议）。

## 1. 做什么，不做什么

两种接收，价值和难度差别很大，应当分开看：

| | 谁来投 | 协议 | 难度 | 价值 |
| --- | --- | --- | --- | --- |
| A. 映湾协议接收 | 另一台装了映湾 Desktop 的电脑 | CastBay Link（已有，TLS + 配对码） | 中 | 自己的两台电脑之间；会议室电脑 |
| B. AirPlay 接收 | iPhone、iPad、Mac | AirPlay（镜像 + 音乐） | 大 | 最大的空白：Windows/Linux 上免费接 iPhone |

不在范围内（至少第一阶段）：DLNA 接收（电视端那套是 Kotlin，且手机用 AirPlay 就够）、AirPlay 视频（YouTube 等“视频投屏”，需要一个 HLS 播放器）、Miracast、Chromecast 接收。

## 2. 现有的东西能复用多少

- **AirPlay 协议核心是现成的 C 代码**：电视端用的是 UxPlay 的 `lib/`（RAOP/AirPlay 协议、FairPlay 的 playfair、llhttp、libplist，加 OpenSSL 的 libcrypto），它自己不带渲染，视频和音频通过回调交出来，在安卓上用 MediaCodec 解码。粘合代码（`airplay/src/main/cpp`）总共约 1500 行，桌面版要换掉的只有三块：mDNS 注册（安卓用 NsdManager）、视频出口、音频出口。
- **Link 协议**：电视端的接收实现（Kotlin，约 980 行：TLS 服务、配对、会话、音频播放）和桌面端的发送实现（Rust，约 920 行）都在，帧格式和配对逻辑一致。接收端用 Rust 重写服务端那一半即可，已经有 rustls、tokio。
- **mDNS**：桌面端已经用 `mdns-sd` 做浏览，它也能注册服务，不需要 Bonjour/Avahi。
- **FFmpeg**：已经静态编译进来，但**目前是 `--disable-everything`，只开了编码器**（libx264、h264_nvenc、aac）。接收要把解码器打开：h264、hevc、aac（AirPlay 镜像的音频是 AAC-ELD，FFmpeg 自带的 aac 解码器支持）、alac（AirPlay 音乐），以及硬件加速（Windows 的 D3D11VA、NVDEC，Linux 的 VAAPI/NVDEC）。这会让 FFmpeg 的构建变大、CI 缓存重建一次。
- **GPL**：UxPlay 是 GPL-3.0，映湾 Desktop 本来就是 GPL-3.0，没有新的授权问题（电视端已经在这样用）。

## 3. 要新做的部分

1. **把 UxPlay 的 `lib/` 编进 Rust 程序**：Linux 用 CMake/`cc` 构建，Windows 用 MSYS2/MinGW 或 MSVC。依赖：libplist、OpenSSL 3（Windows 上要从子模块编，CI 里已经有 MSYS2 + nasm + perl，可以复用）。
2. **渲染**：不能用现在的 Tauri 网页窗口显示视频（网页里的 WebCodecs 在 WebKitGTK 上不可靠）。需要一个原生窗口：SDL2（最省事，YUV 纹理直接上屏）或 wgpu + winit（更“Rust”，工作量更大）。全屏、保持画面比例、鼠标自动隐藏、窗口随投屏出现和消失。
3. **音频**：cpal（WASAPI / PipeWire），带缓冲和音画同步（NTP 时间戳 UxPlay 已经给了）。AirPlay 音乐还要封面、歌名、进度（元数据回调）。
4. **接收端的状态和界面**：桌面端新增“接收”页：设备名、是否开启、验证方式（开放 / 需要确认 / 配对码 / 密码，UxPlay 的 raop 层原本就支持）、当前连接。
5. **系统层面**：投屏中不休眠（已有 Awake）、Windows 防火墙首次弹窗的说明、固定端口（`raop_set_udp_ports/tcp_ports`，便于放行）、开机自启。
6. **A 的服务端**：rustls 服务、配对码显示在接收端的屏幕上、会话收发、解码和渲染共用上面的管线。

## 4. 分阶段和工作量

“人天”按我们现在的做法估计（一个人集中做，含在真机上测），不是日历时间。

| 阶段 | 内容 | 估计 | 产出 |
| --- | --- | --- | --- |
| 0 探路 | 在 R9000 上编译 UxPlay `lib/`，用 `mdns-sd` 注册服务，iPhone 能连上，回调里打印视频 NAL 和音频包 | 2–3 天 | 能不能做的结论；决定渲染方案 |
| 1 Linux 镜像 | FFmpeg 解码 + SDL2 渲染 + 音频 + 基本界面，iPhone 镜像带声音 | 5–7 天 | Linux 上可用的 AirPlay 镜像接收 |
| 2 Windows | 构建链（OpenSSL、MSYS2）、D3D11 渲染、WASAPI、防火墙说明、安装包 | 5–7 天 | Windows 上同样可用 |
| 3 打磨 | 验证方式、AirPlay 音乐（封面、元数据）、全屏体验、稳定性（长时间、断线重连）、诊断 | 5–7 天 | 可以发给用户 |
| A 映湾协议接收 | 复用阶段 1–2 的渲染和音频，写服务端、配对、界面 | 4–5 天 | 电脑到电脑 |
| 合计 | | 约 4–6 周 | |

## 5. 风险

- **苹果协议会变**：iOS 更新偶尔会让第三方接收端失效。UxPlay 上游一直在跟进，我们靠更新子模块。风险和电视端相同，但接收端多一倍。
- **合规与名称**：FairPlay 部分是第三方逆向实现（playfair）。电视端已经在用，桌面版不增加新的类别；产品名里不能写“AirPlay 接收器”这类容易被当成官方的表述（目前电视端的写法可以沿用）。
- **安全面**：接收意味着电脑监听网络端口，处理来自网络的数据（UxPlay 的 C 代码）。要有：默认关闭、清楚的验证方式、不在公共网络自动打开、对协议解析做模糊测试（电视端已有 mDNS 的 fuzz，这里也要加）。
- **Windows 的 mDNS 与防火墙**：装过 iTunes/Bonjour 的电脑会占 5353 端口；`mdns-sd` 用共享端口应该可以，要实测。防火墙首次弹窗必须允许“专用网络”，否则 iPhone 找得到但连不上，用户会以为程序坏了，需要在界面里提示。
- **性能**：4K / H.265 / 高帧率的软件解码会吃力，需要硬件解码；阶段 1 先用软件解码，阶段 3 再接硬件加速。
- **测试成本**：需要 iPhone、Mac、Windows 机器、Linux 机器；每个 iOS 大版本都要复测。
- **维护面翻倍**：从“两个系统上的一个角色”变成“两个系统上的两个角色”。

## 6. 产品形态：会不会乱

- 同一个程序、两个明确的入口：首页“投到别处”和“接收投屏”；“接收”默认关闭，打开后才监听网络，托盘图标显示状态。
- 名字：先保持 CastBay Desktop；如果以后接收端用户多于发送端用户，再考虑拆成独立的应用。
- 文案要避免“同一个按钮既收又发”：投屏出去用“投屏”，接收用“接收”，不混用。

## 7. 建议

1. **先验证需求，再投入**：现在没有任何用户说过想把电脑当接收端（#236 要的是电视接收 Chromecast/Miracast，是另一回事）。在官网反馈页、桌面端设置里放一个“你想用电脑当接收端吗”的入口（用户主动提交），或者看使用统计里 Windows/Linux 的比例，积累一段时间。
2. **要做的话，先做阶段 0（2–3 天）**：它回答“能不能做”，成本最小，而且不改动产品。
3. **阶段 0 通过后再做阶段 1（Linux AirPlay 镜像）**：Linux 上的免费方案现在只有 UxPlay 命令行，做出一个有界面、有声音的版本就已经有价值；Windows 放第二步。
4. **A（电脑到电脑）可以和阶段 1 并行或随后做**，它复用渲染和音频，但服务的人群更窄，不必抢在 AirPlay 之前。
